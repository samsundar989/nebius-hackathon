## Summary

Running `MP4Box -decrypt <cfg.xml> poc.mp4 -out out.mp4` on a crafted MP4 whose meta box items are re-added from memory triggers a heap-buffer-overflow READ in gf_fopen_ex, called from DoWriteMeta while writing the interleaved output file. The process aborts under ASan (SIGABRT, exit code 134).

## Affected Version

master commit `7d451dbd0` (checked out 2026-10-11; libgpac ABI 16.27.0, built with clang/ASan, Linux x86-64). The defect is in the "store full path for info" branch of gf_isom_add_meta_item_extended (src/isomedia/meta.c:1769-1777); code unchanged at master HEAD `8685582` as of 2026-10-16.

## Reproduction

Built from master `7d451dbd0` with `--enable-sanitizer` (ASan), Linux x86-64.

```
MP4Box -decrypt drm_ctr.xml poc_meta_item_path.mp4 -out out.mp4
```

drm_ctr.xml is any valid CENC AES-CTR config (the one used here is attached next to the PoC). The campaign saved 52 crash inputs reaching this exact signature; every one re-crashed on re-run (52/52). The attached PoC was re-verified twice on 2026-10-16.

## Root cause analysis

When the mp4 mux filter re-writes a file whose meta box contains items with inline data, it re-adds each item from memory via gf_isom_add_meta_item_memory (src/filters/mux_isom.c:6068). In gf_isom_add_meta_item_extended, the path stored for such items is allocated and filled without a NUL terminator:

```c
/* src/isomedia/meta.c:1772-1776 */
infe->full_path = (char *)gf_malloc(sizeof(char) * data_len);
if (!infe->full_path) return GF_OUT_OF_MEM;
memcpy(infe->full_path, data, sizeof(char) * data_len);
```

`full_path` is later consumed as a C string by DoWriteMeta when exporting self-contained items (src/isomedia/isom_store.c:900, `src = gf_fopen(iinf->full_path, "rb")`), which reads one byte past the end of the allocation (ASan: READ of size 2, 0 bytes to the right of the region). Any other C-string use of full_path (logging, dump paths) is equally affected.
