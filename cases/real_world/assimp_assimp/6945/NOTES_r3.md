Review of two earlier Leakproof runs on this leak (written by Claude Code from the run records; no gate inputs, tests or test results are quoted here). No candidate was verified.

- Where the leak is: `STLImporter::LoadASCIIFile` allocates one `aiMesh` and one `aiNode` per `solid` block and keeps them only in the local vectors `meshes` and `nodes`. Ownership moves to `mScene->mMeshes` and `root->mChildren` only at the end of the function. Every `DeadlyImportError` thrown between the allocation and that hand-over (node name too long, unexpected EOF while parsing a facet, invalid number of vertices, normal/position buffer size mismatch) leaves the function with every mesh and node created so far unreachable.
- The normal path does not leak: at the end of the function the meshes and nodes are attached to the scene. Run 2's plan said they were never attached; that was wrong.
- Run 1: the one candidate that built freed the meshes and nodes on the non-throwing "unexpected EOF, endsolid expected" `break` path. Execution then continued to the end of the function, which stored the freed pointers in the scene: a new use-after-free. Do not free anything on a path that reaches the end of the function.
- Run 2: the workers tried to rewrite the 200-line function around `std::unique_ptr`. Every attempt failed to build or failed to apply (unbalanced braces). Keep the edit small and local; do not restructure the parser.
- What a reviewer will accept: release what the two local vectors hold only when an exception leaves the function, rethrow the same exception, and leave the success path byte-for-byte unchanged. `aiMesh` and `aiNode` destructors free their own arrays, and at the time of any of these throws neither object is referenced by `mScene` or `root` yet.
